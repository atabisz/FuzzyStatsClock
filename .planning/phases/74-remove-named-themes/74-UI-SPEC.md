## Interaction Patterns

**No new interactions introduced.** This phase removes existing interactions only.

**Deleted interactions:**

1. **Theme card click** (5 handlers deleted)
   - **Before:** Click theme card → `ThemeSelected` event → `ApplyNamedTheme()` → sets accent color, opacity, font size, clock type, stats visibility
   - **After:** Theme cards removed; users interact directly with individual controls (existing pattern)

2. **Theme persistence** (2 sites deleted)
   - **Before:** `SaveSettings()` with-expression includes `Theme = _currentTheme` (line 547)
   - **After:** Individual property values saved directly (existing pattern since v3.2)

3. **Theme restoration on startup** (1 site deleted)
   - **Before:** `ApplySettings()` lines 363-372 check for saved Theme and call `ApplyNamedTheme()`
   - **After:** Individual property values applied directly (existing pattern)

## Migration Contract

**Settings JSON behavior:**

| Scenario | Behavior |
|----------|----------|
| Fresh v4.1 install | No `Theme` field in settings.json; AccentColor used directly |
| Upgrade from v4.0 with `"Theme": "Midnight"` | `System.Text.Json` ignores unknown `Theme` key; loads `AccentColor` field (always persisted individually since v3.2) |
| Upgrade with `"Theme": null` | Same as above; null theme ignored, AccentColor used |
| Upgrade with no `Theme` field | No change; AccentColor loaded directly (already the fallback path) |
| Upgrade with custom hex AccentColor + Theme saved | AccentColor wins (Theme field is never read after v4.0→v4.1 upgrade) |

**No migration code required.** Deletion of `AppSettings.Theme` field makes the type-safe contract reflect runtime behavior (Theme was always advisory; AccentColor was always the source of truth).

**Validation:** `SettingsService.Validate()` has no Theme-related guards. AccentColor uses existing hex validation (regex pattern, unchanged).

**Source:** CONTEXT.md D-01, D-02, REQUIREMENTS.md CLEAN-03
