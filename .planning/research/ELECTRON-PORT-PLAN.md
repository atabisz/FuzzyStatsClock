## TL;DR for the Roadmapper

- **The port is feasible and the resource argument runs *toward* Electron, not against it — and this is no longer a floor-vs-baseline comparison.** The real workload was measured in Phase 1: **8.21-10.88% of one core against WPF's 19.92-20.98%, 1.93-2.43× cheaper**, one instrument, both builds back to back `[MEASURED: ISC-6]`. **Re-measured in Phase 6 with the whole stats pipeline live — two `typeperf` children, a battery poll and a 1s SVG panel repaint — Electron read 9.47% and moved barely at all**, while the WPF baseline came in at **32.19%** on that run: **3.40× cheaper**. Quote the pair from one run and never across runs: the WPF side moved **+7.99pp between the two sessions** on the same host, which is why the ratio moved and the Electron figure did not. The original headline (WPF 24.2% / 326MB against a **parked** Electron overlay at 3.5% / 310MB) stands as the floor it always was, and the real figure landed comfortably inside it. **Memory still does not resolve and the reason is the method** — three runs now, intervals overlapping in both directions every time, so no ordering follows. Disk went the other way, and Phase 7 bought some of it back: **the NSIS installer is 1.27× the Inno one** (69.3MB vs 54.7MB) and the payload 1.20×, down from 1.40× on both measures once 54 unused Electron locale bundles left the package — **40.5MB of the 41.0MB in `locales/`, for languages this app never renders**. Against a ~85MB prior. `[MEASURED: ISC-8, re-run in Phase 7]`
- **The cheap alternative died with this requirement.** WebView2 hosted inside the existing WPF shell reaches the SVG-display goal for roughly a tenth of the work — and it is Windows-only. Asking for macOS and Linux is what makes the full Electron rewrite the only path.
- **Linux is the *easiest* telemetry platform of the three, not the hardest.** CPU, memory, swap, battery and **temperatures** are all unprivileged reads under `/proc` and `/sys`. Windows needs a long-lived `typeperf` child plus a ring-0 driver for temps. **macOS is the hard one** — no unprivileged temperature source and no GPU utilisation without root `powermetrics`.
- **Exactly two capabilities are declared absent on Linux by Electron's own typings**, and they are the only hard API gaps in the whole port: `setLoginItemSettings` (`@platform darwin,win32`) → auto-launch needs a hand-written `.desktop` file; `setContentProtection` (`@platform darwin,win32`) → no self-exclusion from screen capture, which is auto-contrast's feedback-loop guard. Everything else is present-but-unproven, a cheaper class of problem. **Phase 7 resolved the first of the two by not calling the API at all on any platform** — the Windows value name has to be the literal `FuzzyClock` so a v5 install replaces the WPF Run entry, which `setLoginItemSettings` cannot express, so all three sinks are hand-written behind one contract.
- **One decision gated the plan and only Alex could make it: temperatures. ~~Open~~ DECIDED 2026-08-28 — Option C, drop them, on evidence Phase 1 produced.** See § The one decision below; the sidecar was built and measured before being deleted, and the reason it lost was not its size.
- **Do not build the shell first.** The overlay window, tray, click-through and ghost-mode designs are already proven in `~/code/garry-desktop`, so building them first *feels* like progress while learning nothing. **Phase 1 is the telemetry spike, and it is the go/no-go.** *(Held: the spike ran first and the shell landed as Phase 3 — and it was right to distrust the borrowed design. `garry-desktop`'s flag set transferred, but its window-traits probe did not: it scans by process **name**, which on this box would attribute another Electron app's window to the overlay, so `winflags.ps1` takes a pid instead.)*
- **PERF-01 — the v4.4 fade stutter, deferred three times — is closed as a comparative claim, and the architecture is the reason.** The fade interpolates on the **renderer's** `requestAnimationFrame` and writes a composited SVG attribute, so a saturated main process delays *where the fade is going*, never *how smoothly it gets there*. Measured against a v4.4-shaped `setOpacity()`-from-main control built into the same process: the pump holds **median 11.8 ms flat** whether main is idle or blocked 40 ms out of every 50, while the control goes **30.0 → 62.0 ms** `[MEASURED: probe:fade, 8 phases]`. **The provisional caveat is discharged: re-run from an unlocked desk, `probe:fade` reads 8 of 8 blocking arms green** and F0 now matches a real panel — 11.8 ms is ~85 Hz against a 90 Hz display, where the locked run's 12.7 ms / ~79 Hz matched nothing. § Phase 5.
- **Cost centre is not the shell and not the display.** It is **2,467 LOC** of `FuzzyClock.Core` plus **632 tests** (469 Core + 163 App) to re-earn — of which **578 survive Option C** — and the three Windows telemetry paths. All three figures were re-measured on the branch and all three moved: the LOC lost `TemperatureFormatter.cs`, the App count was **633 quoted and 632 measured**, and 54 of the 632 cover temperatures.

**Ten probes now answer ten different questions, and running a subset hides whichever half it does not reach — and `probe:mac-package` adds an eleventh question that none of them asks: does the SHIPPED BUNDLE run.** `probe:shell` reads the *window* off Win32; `probe:display` reads the *document* off CDP; `probe:fade` reads a *frame clock* against a negative control; `probe:pixels` reads **an actual pixel off the glass**, which nothing in this tree could do before Phase 5 (`probe-display.ts:64` said so); `probe:battery` reads **a live source's cadence over 30 seconds**, which no fixture can, because a parser cannot fail to arrive; and Phase 7 adds two that read **state outside this process entirely** — `probe:autolaunch` reads the Windows registry back through a *second* reader after the app's own writer put it there, and `probe:update` reads a real HTTP answer off api.github.com. Phase 4 broke `probe:shell`'s size arm by making the window's size a renderer decision; Phase 5 broke its `layered` arm by removing main's `setOpacity` call; **Phase 6 broke nothing in `probe:shell` and instead found that one of `probe:display`'s own greens had been asserting a defect as correct behaviour** (D6, the date font); **Phase 7 broke nothing and instead found that two of `probe:size`'s own prose notes had gone stale** — they still said the locale trim was "deliberately not taken" and that no icon was set, after the change that took both. **Four times the expectation or its description was the stale thing, and each time it took a different instrument to establish that.** **The borrowed mac added two more probes and a fifth instance of that pattern, and the fifth one was in the tests rather than a probe:** `probe:icon` reads *artwork*, which is a modality nothing here had — it compares rendered pixels against the shipped raster and mutates its own inputs to prove the comparison bites — and `probe:launchd` reads **another OS's service manager**, which is the first arm on this port to prove a file we write is honoured by something outside our process on a platform that is not Windows. **A tenth arrived after those two and reads a modality none of the others do: a distribution rather than a decision.** `probe:cpu-counter` samples the host's tick counters hundreds of times and reports rates, worst cases and a run-length histogram, because the thing it characterises is intermittent — and every other probe in this tree answers a yes/no question a single observation can settle. The fifth stale expectation: `dial-geometry.test.ts` asserted bit-exact equality on trig-derived doubles, which is over-specified rather than wrong, and 13 of 376 fields diverge by 1-4 ULP on arm64 because ECMA-262 does not bit-specify `Math.sin`/`Math.cos`. **Fixed by enumerating the two architectures' exact values, not by adding a tolerance** — and it was the file's own docblock that had prescribed that remedy before the divergence existed. **A sixth arrived last and is the only one that was intermittent rather than wrong-on-every-run**, which is why it survived every previous gate: `cpu-delta.test.ts` asserted that two real CPU snapshots 60 ms apart cannot come back `UNAVAILABLE`, and on Windows a per-core `idle` tick counter goes *backwards* between ordinary reads often enough to fail one full-suite run in four. **And a seventh is different in kind from the other six, which is why it is worth listing separately: it was not a stale expectation but an unsound derivation, in the fix for the sixth.** The retry bound that repaired `cpu-delta.test.ts` was set at 10 from a `p^10` exhaustion probability — arithmetic assuming the samples were independent. Promoting the throwaway probe into `probe:cpu-counter` and having it print a run-length histogram showed they cluster (runs of 7, where independence predicts 4.6e-3 of them), leaving that bound at 1.4× of observed behaviour. **And an eighth is the shortest-lived of them all: a probe row and three code comments that went stale within a day of being written.** The Ubuntu run closed the `probe:cpu-counter` Linux gap on the same day the gate row above was asserting that gap as the probe's reason to exist, and three source comments said "Linux has never been measured" for a few hours after it had been. All four are retracted in place with a date rather than overwritten, because the two-platforms-clean conclusion is what downgrades the finding from a product risk to a Windows-only test problem, and a conclusion should carry the date it was reached. **Eight times now, the expectation, its description or the reasoning behind it was the wrong thing, and no two took the same instrument to establish.** The seventh is the one that most nearly escaped, because the fix it was part of was already green; the eighth is the one that says a document can be stale without anyone editing it — the world moved instead. **And a ninth arrived with Phase 6.5, in a probe's first run rather than in an old row: H5 was written expecting the settings window's always-on-top to be OFF and read `true`.** Nothing in the port requests it, so the owner relationship propagated `WS_EX_TOPMOST` — which turned `settings-window.ts`'s documentation-argued claim into a measured one and split the arm in two (**H5b**, `!IS_MAC`). It is listed with the other eight because it is the same shape: the expectation was the wrong thing, and only an instrument reading the live object could say so. **Phase 6.5 also brings the tree to 20 `probe:` entries in `package.json` over 19 distinct scripts** (one of the twenty is `probe:settings-window:control`, the same script with its mutation flag), and the paragraph above's "ten" is left standing as the count it was true for rather than being quietly incremented each phase — the point it makes is about *modalities*, and 6.5 adds two. `probe:settings-window` reads a **second window under a strict CSP**, where every other probe here reads the overlay. `probe:mac-focus` reads **which window the keyboard is aimed at**, which is a modality nothing else in the tree touches: every other probe asks whether something is *there* or *correct*, and this one asks where the user's next keystroke lands. **And it carries a tenth instance of the stale-expectation pattern, this time in a control rather than an arm** — F8 was authored asserting "the app was never activated" for a mode that still had the activation call live in it, so the expectation was wrong when written, and the reading it actually produced (the overlay took key, not the settings window) was the more useful finding. That is the one that turned a redundant call into a *wrong* one and decided the deletion.

## The one decision

**What happens to CPU/GPU/motherboard/NVMe temperatures?**

`FuzzyClock.App/TemperatureService.cs` is built on `LibreHardwareMonitorLib 0.9.6` — a .NET library plus a ring-0 WinRing0 driver. There is no Node equivalent and there is no unprivileged Windows API that reads real sensor temperatures (`MSAcpi_ThermalZoneTemperature` is unimplemented or meaningless on most desktops). `[MEASURED: TemperatureService.cs:13, FuzzyClock.App.csproj:15]`

| Option | Windows | macOS | Linux | Cost |
|---|---|---|---|---|
| **A. Sidecar (recommended)** | Full fidelity — keep LHM in a ~100-line .NET console app writing one JSON line per 2s to stdout | `--` (unavailable) | Full fidelity via `/sys/class/hwmon` | One extra build target; Windows installer carries a self-contained trimmed sidecar. **Size is a Phase 1 measurement, not an assertion.** |
| **B. Linux only** | `--` (regression on the primary platform) | `--` | Full fidelity | Cheapest. Loses a v4.2 feature where it is most used. |
| **C. Drop temps** | `--` | `--` | `--` | Cheapest of all; deletes a shipped feature and its settings UI. |
| **D. `nvidia-smi` for GPU temp only** | GPU temp only, NVIDIA only | same | same | Nearly free — `nvidia-smi` is present here and answers in 0.378s `[MEASURED]` — but vendor-locked and no CPU/mobo/NVMe. |

**Recommendation was A.** The sidecar looked like the one place a second language earns its keep — the logic already exists, the process boundary naturally isolates the **608ms mean `Update()` cost** the WPF app already worked around with a dedicated 2s loop `[MEASURED: TemperatureService.cs header]`, and .NET never ships to macOS or Linux. The recommendation came with its own condition: **A is not free and its size is unknown; Phase 1 produces the number before this is committed to.**

### DECIDED 2026-08-28: **C — drop temps.** Alex's call, on Phase 1 evidence that the table above did not have.

The number Phase 1 produced was not the one that decided it. Option A came in at a very affordable **17.0MB trimmed** with a **106.8ms** mean read — both better than this table assumed. What decided it was `probe-sidecar.ts`'s coverage arm: **unelevated, the CPU node enumerates 51 temperature sensors and every one reads NULL.** Only GPU answered (NVAPI needs no ring-0 driver). So "full fidelity" in row A is conditional on an elevation manifest — a UAC prompt at every launch of an autostarting overlay — and **without it row A delivers exactly what row D delivers nearly free.** Full evidence: ISA ISC-9. The sidecar was built, measured and then deleted; its code is at `64c747e` if the decision is ever revisited.

Everything downstream is unaffected, and that was true whichever row won: the stats panel already renders `-1f` as unavailable, so a platform with no temperature source degrades through a path that already exists and is already tested. Under C that path is the only path, on all three platforms.

**Two macOS measurements changed a cell each, in opposite directions.**

`os.freemem()` returned **264,617,984 of 8,589,934,592 bytes — 3.1% free — on a healthy,
responsive machine.** It is not a memory-pressure signal on macOS; it is the free-page count,
and macOS keeps that near zero on purpose. So the macOS MEM cell is computed from `vm_stat`,
not from `os.freemem()`, and the plan's original "`os.totalmem/freemem` + `vm_stat` for the
compressor" had the primary and the supplement the wrong way round. The occupancy figure is
`(active + wired + occupied-by-compressor) / total pages` — **69.14%** on the captured
snapshot, against the 3.1% `os.freemem()` implies. A cell that reads 97% used when the machine
is fine is worse than a cell that reads `N/A`.

`ioreg -r -c AGXAccelerator -l` returns GPU utilisation **with no privileges**, which the plan
had written off. It is an undocumented IOKit path on an Apple-silicon-only driver class, so it
is a candidate rather than a decision — but a candidate is not a `-1`, and the row above says
so now. Fixture and caveats: `electron/test/fixtures/README.md`.

### Three rules that fall out of the measurements

**1. Poll cadence is per-metric, not global.** Per-tick shell-outs are ruled out by measurement: a one-shot `typeperf` sample costs **2.81s** wall and `Get-Counter` **2.55s**, against a bare process start of 0.17s / 0.51s `[MEASURED]` — untenable at the app's 1s interval, let alone its 0.5s hover fast-refresh. But a metric that moves slowly does not need the tick:

| Cadence | Metrics | Mechanism |
|---|---|---|
| 1s (0.5s on hover) | CPU, MEM, GPU, PAG | **one long-lived child**, streaming |
| ~~2s~~ | ~~temps~~ | **no longer exists — Option C.** The 2s tier had exactly one occupant, so retiring temps retires a whole cadence and the process that served it |
| 60s | battery | spawn-per-poll is fine at this cadence |
| free | uptime | in-process |

**2. The Windows child works, including the GPU wildcard, and has one known fidelity defect.** `typeperf "\GPU Engine(*engtype_3D)\Utilization Percentage" -si 1` streams CSV and accepts the wildcard, but returned 0.000000 while `nvidia-smi` read 10% in the same minute: **PDH resolves instance names at spawn, so GPU engines belonging to processes started later are invisible** `[MEASURED, with a positive control — the `\Processor(_Total)` column in the same run moved, so the child was live]`. Design consequence: the child must be **periodically recycled**, or the GPU counter re-enumerated, exactly as `StatsService.cs:159-176` already does in-process on `InvalidOperationException`. Carry that behaviour across; do not rediscover it.

**3. `MEM` means something different if you take the easy road.** The WPF app reports **commit charge** (`% Committed Bytes In Use`), which read 97.5% here. `os.freemem()` reports *physical* free. Those are different numbers about different things, and swapping one for the other silently changes what the widget says. If the counter child is dropped on Windows, the settings UI and the docs have to say "physical", not "committed".

### Two places the port should be *better* than the original

**1. ~~The fade may stop freezing under load.~~ It does not freeze under load — measured 2026-08-30.** `.planning/STATE.md` carried v4.4 **PERF-01** — the ghost fade freezing under 25–50% CPU load — deferred to v4.6+. The design was as predicted: the interpolation runs on the renderer's `requestAnimationFrame` and writes a composited property, with main pushing only the *target*. `LerpRatio` is already frame-rate-independent (`alpha = 15.0`) and dropped straight in.

One word in the prediction is worth correcting, because it names the wrong reason for a right conclusion. **"A compositor-thread opacity animation does not stall when the main process is busy"** — an `opacity` attribute rewritten from JS every frame is not a compositor-thread *animation*; it is a renderer-main-thread write, like any other DOM mutation. `opacity` being a composited *property* is what stops the subtree re-rasterising (which is why the rule below matters), but it is not what makes the fade survive load. **What makes it survive is that the renderer is a different process from the one that is busy**, plus `backgroundThrottling: false` on the window. That distinction is not idle: it is exactly why the fade would still have stalled had the pump been written in main with `setOpacity`, composited property or not.

Measured either way: **the pump holds median 12.7 ms with main blocked 40 ms out of every 50, while a `setOpacity()`-from-main control in the same process goes 31.0 → 62.0 ms** `[MEASURED: probe:fade]`. **The claim was carried, not hoped — and one arm of the probe exists purely to prove the load arrived, because a flat line under a load that never landed is indistinguishable from success.**

**2. The display becomes native to the medium.** The dial is a `Canvas` 80×80 with two `Line` hands about centre (40,40) and `DialGeometry.cs` is **19 LOC** `[MEASURED]`; LCD is `SevenSegmentEncoder.cs`, **27 LOC**. Both are more natural as SVG than as XAML.

**The one hard SVG performance rule, from his own measured work:** `transform` and `opacity` are **composited**; `r`, `rx`, `ry`, `cx`, `cy` and `d` **re-rasterise every frame**. So animate the clock hands with `transform="rotate(θ)"` on a `<g>`, never by rewriting `x2`/`y2` on a `<line>`; and build the Nixie glow as a static SVG filter, not a per-frame geometry change.

## Linux scope

**Target X11 / XWayland for 1.0. Native Wayland is out of scope.** Three mechanisms drive that, all `[UNPROBED]` here and all needing a real Wayland session to settle:

1. **Window placement is compositor-owned under Wayland** — a client cannot set its own absolute position, which is the whole basis of a draggable, per-monitor-remembered overlay.
2. **Global cursor position** — `screen.getCursorScreenPoint()` carries no `@platform` restriction `[MEASURED: electron.d.ts:10864, and the annotation demonstrably appears elsewhere in the same file, so its absence is information]`, but Wayland has no protocol for a client to query the pointer outside its own surface. Ghost mode is built on exactly that query.
3. **No capture self-exclusion** (see the table) plus a per-session portal prompt for any screen capture.

**Mitigation:** `app.commandLine.appendSwitch('ozone-platform', 'x11')` to force XWayland, where all three work as on X11. Ship that, document it, and revisit native Wayland only if someone asks.

**Status 2026-08-30:** the X11 path is smoked — `forceX11OnLinux` fires and the switch propagates to the `--type=gpu-process` child (`--ozone-platform=x11` in its argv), the frameless window maps, `type: "toolbar"` applies, and placement restores. That was on an **X11 login session**, so it exercises the mitigation's target directly; a Wayland session forcing XWayland through the same switch is still `[UNPROBED]`, as is native Wayland. Window placement (1) and cursor position (2) were exercised on X11 and behave; capture self-exclusion (3) is untested on any Linux.

#### S2 was a red blocking gate, it was not waived, and the pixels settled it

|---|---|---|
| `transparent: true`, nothing called | false | false |
| after `setIgnoreMouseEvents(false)` | false | false |
| after `setIgnoreMouseEvents(true)` | **true** | **true** |

#### Two C# defects reproduced, one closed — and the standard used to decide which
`GhostSampler.deactivate()` writes two fields. #### Two deviations from `OnRenderingTick`, both in `core/ghost-fade.ts`'s header
- **An epsilon snap, because the C#'s convergence test is unreachable for an intermediate target.** A cursor parked partway into the halo gives a target like 0.8, which the exponential approaches and never equals — so `_currentRatio == _targetRatio` never holds and WPF's `Rendering` handler stays attached forever, ticking at compositor rate for a value that stopped changing.
- **A converged frame still writes once if a guard swallowed the write.** In the C# the guards return *before* the write while step 3 has already advanced the ratio, so a guard held long enough to converge means the write never happens: start a drag, move onto the widget, target snaps to 1.0 under `_isDragging`, and **the widget stays at full opacity for the rest of that gesture while click-through is active.** `skipped` is a *reason* rather than a boolean precisely so the owed write can be landed on the first unguarded frame.

#### One decision made in the tray, and the open question it is built around
RMB-04's `_menuOpen` pin exists so the widget cannot fade out from under its own menu. #### D11b, the arm that would have caught it — and the seventh invisible-divergence class

`probe:display` gained a blocking arm reading `#uptime` off the live DOM with **three independent halves**, because any one of them alone passes on a broken line:

- **SHAPE** — the C#'s field count and its **3-then-2** spacing, off the live DOM. A renderer that drops the averages again fails here, and so does a tidy-up that normalises the two gap widths to one.
- **VALUE** — the uptime field against `os.uptime()` read **in the probe process at the same instant**. - **FED** — at least one average above zero, read after a CPU sample has provably arrived.

**FED exists because of a class of defect this port had not hit before: an arm that is well-formed and *undiscriminating*.** `0.00  0.00  0.00` is a perfectly valid uptime line *and* exactly what an empty queue produces. The six earlier members of this class are listed across §§ Phase 4 and 5; this is the seventh and the first where the *arm* rather than the *code* was the thing that could not see.

**And the harvest's own window could not answer FED, measured rather than assumed.** A throwaway instrument drove the shipped `Win32StatsSource` under plain `bun`: at a 1 s cadence the first battery sample lands **+1072 ms**, the scalar header validates **+2138 ms**, the GPU header **+2822 ms** (318 3D instances), and the **first CPU sample +3149 ms** — a ~2.1 s PDH header handshake plus one whole interval. `DEFAULTS.statsIntervalSeconds` is **2.0** and `createStatsSource()` takes the constructor default of 1, so main's `setIntervalSec(2.0)` respawns both children and pushes the first reading to **≈4.1 s** — against a harvest whose last sample is taken at about `PROBE-READY` + 4.5 s. A coin flip, and the losing side is unreadable rather than red. So the harvest's timing is left untouched and D11b takes its **own** read: poll `#cpuText` until it carries a percentage, wait one repaint tick, then assert. Measured cost, five launches: the wait resolves at **+2615 to +3826 ms**, and every case reads live averages over a live row — `up 17d 1h 32m   0.46  0.46  0.46` over `#cpuText` `"46%"`, and four more like it between 0.24 and 0.67.

#### The `Np` field is a measured remainder, and both Windows mechanisms are ruled out on this tree's own numbers

The `14p` field is **not** a process count — it is the number of processes that used at least `processCountThresholdPercent` of the machine's *whole* CPU capacity in the last interval (`MainWindow.xaml.cs:1230-1269`). `core/process-count.ts` transcribes the derivation, including the `ProcessorCount` divisor that makes a fully-saturated single core read **3.125%** on this 32-core host and therefore *not* register against the 5% default. What is missing is acquisition: **Windows has no per-process cumulative-CPU-time API for Node**, and both shell routes are already refuted here —

- `typeperf "\Process(*)\% Processor Time"` inherits **P1.2's measured defect**: PDH resolves instance names at spawn, so processes started later are invisible. For a count of *active* processes that is not a fidelity nick, it is fatal.
- a per-tick one-shot costs **2.55 s (`Get-Counter`) / 2.81 s (`typeperf`)**, measured in Phase 1 against a 1 s cadence.

So `uptimeLine` takes `procCount: null` and **drops the field rather than printing `0p`** — `0p` is a legitimate reading the C# renders on its first tick, so a zero-instead-of-absent would be indistinguishable from a real count. D11b treats `Np` as optional and **reports which side it saw**, so paying this remainder shows up as a changed detail line rather than as a failure. On macOS and Linux the per-process times are cheap (`/proc/<pid>/stat`, `ps -eo`), so this is a Windows blocker rather than a design one.

#### Auto-launch is one contract over three sinks, and `setLoginItemSettings` was rejected on three separate grounds

- **The signature is not paid, and the build log actively misleads about it.** electron-builder prints `signing with signtool.exe`; `Get-AuthenticodeSignature` reads **`NotSigned`** on the installer *and* on `win-unpacked\FuzzyClock.exe`. #### `main.ts`'s two seams moved into their own module so the probe drives the app's adapters, not a copy

#### After Phase 7 closed: the 512px icon, the borrowed mac, a retracted claim, and two defects in our own suite
Alex's ask was two things — *"macos should be available via the codex mcp, create a suitable 512px icon ourselves, go"* — and the second turned into three purchases. **The MCP path idled out at 900 s and `ssh` replaced it**, on his own instruction; every figure below came off `alex@10.127.60.135`, a macOS 26.6.2 arm64 host.

**The icon is redrawn, not resampled, and the geometry recovery has its own tell.** Upscaling the 256px raster to 1024 would have satisfied electron-builder and looked wrong on a Retina dock. `scripts/make-icon.ts` reconstructs the dial from parameters recovered off the shipped raster, and **those parameters landing on a round grid is the evidence the recovery is right rather than fitted**: outer 0.48·S, ring inner 0.40 (a 0.44·S circle stroked at 0.08·S), hub 0.09, minute hand at 60° length 0.34, hour hand at 300° length 0.22. `probe:icon` holds the result to the shipped raster on **two** error scales — a global premultiplied MAE (0.402/255) that is blind to a small localised error, and a worst-16×16-tile MAE (1.848/255) that is not — each limited at the geometric mean of measured residual and weakest mutation.
**A comparison whose best case is guaranteed needs mutations, and the probe says that about itself.** A3 downsamples our render back to 256 before comparing, which flatters a systematically wrong redraw; A4 therefore perturbs one parameter at a time, six ways, and every mutation must break the comparison. The weakest sits **3.74×** its limit.
**The 512 floor stopped being folklore — and measuring it showed half of what we had said about it was wrong.** It had been quoted in three files as the reason `mac.icon` and `linux.icon` were absent, always as a citation. Pointing `mac.icon` at a 256px downsample of our own file now fails with **`Icon must be at least 512x512 pixels, provided: 256x256`** (`app-builder-lib/src/util/iconConverter.ts:307`, exit 1) — so the claim that the old `app.ico` would have *failed the build* rather than skipped the icon is a run. But **the floor is icns-only**: the same 256px file goes through `format: "set"` at exit 0, so `linux.icon` was never blocked by it. See the Linux paragraph below for the retraction.
**What the mac bought, at artefact level.** `dist:mac` exit 0 → an 87,794,076-byte dmg carrying a 174,738-byte `icon.icns` generated from our PNG, whose `iconutil -c iconset` ladder is complete at eleven images with **pixel dimensions checked one by one rather than read off the filenames** — worth doing, because two pairs share a byte size and look like duplicates until measured. `LSUIElement`, the category and the appId all read back out of the built bundle's `Info.plist`, so the whole config validated as written. The artwork was **viewed**, decoded back to PNG through macOS's own icns decoder: dark disc, white hub, hands at ten and two. And `build/icon.png` regenerated from transferred source is **byte-identical** to the Windows one — container and decoded-pixel sha256 both match, so the generator is deterministic across architectures and not merely repeatable.
**`dist:mac` HANGS under bun-standing-in-for-node, and the diagnosis was CPU-time-vs-elapsed.** The Mac has no system `node`, and `bun run` substitutes itself for a `#!/usr/bin/env node` shebang — which electron-builder's bundled `icon-tool.js` has, driving `vips.wasm`. It never returns: **28 minutes elapsed for 19 seconds of CPU**, no error, no timeout, empty output directory. Elapsed time alone reads as a slow build; **the ratio is what distinguishes a hang from slow work.** Real node v24.20.0 in `/tmp` finishes the same command in about a minute. Written into `electron-builder.yml` for whoever runs it next.
**The Linux half splits cleanly, and the first draft of this paragraph got the split WRONG — that retraction is the more useful finding.** It said: *"The icon-set conversion — the exact code path `linux.icon` drives — emitted all eight sizes at exit 0."* Neither clause holds. `convertIcon({format: "set"})` on our 1024 PNG returns `[{file: build/icon.png, size: 1024}]` — the source **handed back as-is, no ladder at all**, `iconConverter.js`'s own branch comment reading `set: source is already a .png — return as-is with its dimensions`. And **the 512 floor is icns-only**: measured both ways on a 256px downsample, `set` returns `[256]` at exit 0 while `icns` throws `ERR_ICON_TOO_SMALL`. So `linux.icon` was never the blocked half — `mac.icon` was, and three files had said otherwise for weeks. What Linux ships is one 1024×1024 PNG, which is what freedesktop wants.
**How the false claim survived is the part worth carrying: it was read off a build log for a step that build never ran.** `dist:linux` dies at AppImage *assembly* — `spawn EBADARCH (86)`, macOS refusing to exec electron-builder's downloaded Linux `mksquashfs` — and it never reaches the icon step at all: `release/.icon-set` does not exist on the host that supposedly produced it, and `grep -in icon` over a fresh run's log returns **zero lines**. The claim went into `electron-builder.yml`, `probe-icon.ts`, `probe-size.ts`, the ISA, this file and a commit message before **looking for the artefact** falsified it. Corrected in place at every site rather than deleted, and the commit was amended before any push. The AppImage failure itself is unchanged and still a host-tooling limit cleanly separated from the icon question — which is why Linux needs a real host rather than anything in the config.
**Darwin auto-launch is no longer inferred.** ISC-30's A9 had said in its own text that whether `launchd` honours the file needs a real host, so the host got a permanent instrument rather than a transcript: `probe:launchd` (9/0) drives the shipped `main/auto-launch.ts` through the **production** seams, `plutil -lint` validates the plist with a real parser, `launchctl bootstrap gui/501` registers it, and a marker file polled 40×100 ms proves the program was **executed**. **A7 is what makes A6 mean anything** — a byte-identical plist minus `RunAtLoad` registers fine and writes no marker, so A6 cannot be explained by `bootstrap` starting the job as a side effect. Alex's six real LaunchAgents were censused by sha256 before and after: `missing=[]`, `changed=[]`, `added=[]`. **The mac found a real defect in our tests, and enumeration beat tolerance.** Seven failures, all in `dial-geometry.test.ts`: 13 of 376 fixture fields diverge by **1-4 ULP** on arm64 (max absolute 1.421e-14 on an 80-unit dial) because ECMA-262 does not bit-specify `Math.sin`/`Math.cos`. The remedy is an exact two-element set per field — **the fix the file's own docblock had prescribed before the divergence existed** — not a blanket epsilon, and not the tempting "add N ulps to the recorded value", which is unsound because the ULP step changes at every power of two. Non-divergent rows keep `toBe` so the table cannot quietly grow, and an absent coordinate falls through to the exact assertion so a short fixture array fails loudly. One file changed; **2428 / 0 on both architectures.**
**And a cross-host difference was chased rather than waved at.** 279,775 expects here against 279,511 there on the same 2428 tests. No test file reads `process.platform`, so per-file diffing pinned it to `cpu-delta.test.ts:162` looping `os.cpus()` at 11 expects per core — 32 cores against 8, exactly 264.
**Then the retraction's own gate run found a second suite defect, and this one was intermittent.** `bun test` returned **2427 / 1** on a set of edits that were entirely prose — `cpu-delta.test.ts` asserting that two real `os.cpus()` snapshots 60 ms apart cannot yield `UNAVAILABLE`, on the reasoning that "60 ms is several ticks, so the counters must have moved". The ticks do move: a 400-trial probe on the **summed** delta found zero zero-deltas, minimum 1262 ms. **Ruling out the obvious explanation is what forced the real one** — the module's *backwards* guard, firing for a cause its docblock had not listed. Per-core: **a per-core `idle` counter regresses between two ordinary reads, by as much as −312 ms**, on an idle desktop with no sleep and no core going offline. **Real node v24.20.0 reproducing it is the discriminator**: bun alone would have made it a runtime bug worth working around; both runtimes showing it makes it the Windows per-processor counter, which this port cannot fix and should not try to.

**The rate is run-to-run variable, and an earlier version of this section said otherwise — the second retraction of the day, and the same defect as the first.** It read "38 of 600 under bun (6.3%) and 69 of 600 under real node (11.5%)" and treated the 6.3-vs-11.5 gap as a runtime difference. Five runs now: **6.0%, 6.3%, 11.2%, 13.7%, 16.4%** — bun landing above node's figure, and the *lowest* of the five coming from the most heavily loaded run, so the variation is not even monotonic in load. What survives is the qualitative claim, which is the one that mattered: both runtimes show it, so it is the kernel's. `bun run probe:cpu-counter` is now the way to get a figure, rather than any document asserting one.
**The platform that ships this module was measured, and it is the reason this cost a gate rather than a feature.** `cpu-delta.ts` is the macOS/Linux CPU source — Windows takes CPU from `typeperf` — and the same probe on macOS arm64 was **0 of 600 under both runtimes**. A 6-12% per-sample rate there would have flickered the CPU row to `N/A` about twice a minute. Linux is still unmeasured and is stated so rather than inferred from macOS.
**The fix retries the sample and does not loosen the assertion, and the retry path is exercised rather than merely present.** `busy === UNAVAILABLE || in range` would have passed against a function that returns nothing else, so the arm samples until a reading is available, still demands a real percentage in `[0, 100]`, and reports the attempt count on exhaustion instead of failing as `-1 !== -1`. Each attempt spends one `expect` on its busy loop, so **a retry is visible in the expect() count** — over 120 runs of the file as it now stands: **119 at 383, 1 at 384, 0 failures.**

**The bound is 40 because the probe falsified the arithmetic that set it to 10, and that is the third retraction.** 10 came from a per-sample rate raised to the tenth power — 3.2e-10 — **which assumed the samples were independent, an assumption nobody had checked.** Promoting the throwaway into a permanent probe (`probe:cpu-counter`, 4 arms) and having it print a run-length histogram checked it: over 2000 pairs, `1x139 2x49 3x17 4x6 5x2 7x1`. **A run of 7 consecutive UNAVAILABLEs, where independence predicts one that long 4.6e-3 times** — and a second run of 7 turned up inside a later 600-pair run, so runs that long are ordinary. The regressions **cluster**, which is physically unsurprising (whatever accounting transition regresses a core's idle tick does not resolve inside 60 ms), and the tail decays slower than geometric, so no closed-form bound from the per-sample rate is trustworthy. A bound of 10 against an observed 7 is **1.4× of headroom** — the state a suite is in shortly before it goes intermittent again on someone else's machine. 40 is 5.7×, and costs nothing whenever the first sample succeeds, which is almost always. The probe's A4 arm now **reads that constant out of the test file** rather than duplicating it, and demands 2× rather than merely "larger" — the criterion that fails the original 10. Mutation-controlled by patching the constant to `4` and watching A4 report *"bound of 4 (read from the file) … margin 1.3x, need 2x"* and FAIL.

**One more thing the promoted probe bought, which the throwaway had no reason to print: the probe's rate is an upper bound on what the suite sees, not a prediction of it.** An intermediate 120-run tally read **120 of 120 at 383** — the retry path never taken — minutes after the probe measured 13.7% on the same host. The probe loops back-to-back in one long-lived process; the test takes a single sample in a freshly started one. Provoking the 1-in-120 above needed the probe running alongside as a load generator. This is why the section states a band and no model.
**What is still not bought:** any AppImage, any Linux desktop drawing the icon, a signature on either platform, and **a login on any of the three** — the mac agent was bootstrapped into a running session by hand.
