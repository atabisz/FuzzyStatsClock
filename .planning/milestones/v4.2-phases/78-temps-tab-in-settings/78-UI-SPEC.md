# Phase 78 — UI Design Contract

> Visual and interaction contract for the **Temps** tab in `SettingsWindow`.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Platform reality:** This is a WPF desktop widget on .NET 10, Windows-only.
> There is no React, no CSS, no Figma, no shadcn registry. The "design system"
> is the existing `SettingsWindow.xaml` — Dark theme, inline XAML,
> `SegmentButtonStyle` for segmented toggles, and a muted `#FF999999`/`FontSize=11`
> TextBlock convention for help text. All contract values below are derived from
> production precedent in `SettingsWindow.xaml`; this spec binds the Temps tab
> to exact parity with the Stats and Behavior tabs.

## Color

The Temps tab is pure chrome on the existing Dark theme — no accent color, no destructive actions, no brand color, no semantic color. The widget's user-customizable accent color is **not** used inside `SettingsWindow` (SettingsWindow is its own Dark-themed UI chrome; the accent color lives on the widget itself).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Dark theme default (~`#FF2B2B2B`) | TabItem body background inherited from `ThemeMode="Dark"` |
| Secondary (30%) | Dark theme default (~`#FF3A3A3A`) | Control surfaces (CheckBox, TextBlock backgrounds) inherited from Dark theme |
| Muted text (10%) | `#FF999999` | Help text disclaimer only (TEMP-TAB-03 wording) |
| Disabled state | WPF default disabled brush (~50% luminance on Dark theme) | Disabled sensor checkboxes when `IsEnabled=false` (N/A sensors and master-off sub-panel) |
| Accent | not used | The widget's user accent color does NOT bleed into the Settings window |
| Destructive | not used | No destructive actions in the Temps tab (toggles are reversible + non-destructive) |

**Accent reserved for:** the widget itself (MainWindow text) — **NOT used inside SettingsWindow**. Explicit: the Temps tab renders no accent-colored element.

## Temps Tab Composition

Tab body wraps a single `<StackPanel Margin="12">` (mirrors every other tab). Inside, the vertical sequence is:

1. **Master toggle** — `<CheckBox x:Name="ChkTempsVisible" Content="Show Temps Line" Margin="0,0,0,10">` (mirrors `ChkStatsVisible` at line 288–290 exactly — same copy shape "Show {X} Line/Panel", same bottom margin, same wiring).
2. **Sub-panel** — `<StackPanel x:Name="TempSensorsPanel" Margin="16,0,0,0">` wrapping:
   - a per-sensor `<WrapPanel Width="270">` containing 4 fixed-width checkboxes, followed by
   - the help-text `<TextBlock>` (muted, 11px, wrap, verbatim disclaimer copy).
3. **Nothing else** — no section header, no separator, no additional controls in this phase.

### 2a. Per-sensor WrapPanel geometry

| Property | Value | Source |
|----------|-------|--------|
| Container | `<WrapPanel Width="270">` | Stats tab precedent (line 309) |
| Child checkbox width | `Width="86"` | Stats tab precedent (line 310) |
| Bottom margin on wrap-row children | `Margin="0,0,0,5"` | Stats tab precedent (line 310–315 — first-row items get bottom margin so two rows breathe) |
| Number of checkboxes | 4 | one per sensor kind |
| Ordering (locked, left-to-right, row-major) | **CPU, GPU, Mobo, NVMe** | TEMP-TAB-03 + REQUIREMENTS.md order |
| Rows on a 270px canvas with 86px children | **2 rows of 2** (2×86=172, gap+slack absorbs the remaining 98px) OR a single row of 4 if WrapPanel collapses (but 4×86=344 > 270, so 2×2 is the deterministic layout) | arithmetic |

**Why WrapPanel not StackPanel-horizontal:** WrapPanel guarantees graceful reflow if a future phase raises `Width` or the label length grows (e.g. the " (N/A)" suffix adds ~6 chars). A `StackPanel Orientation="Horizontal"` would require label widths to be hand-tuned. Match Stats tab precedent exactly.

### 2b. Help text placement

Placed **directly below** the WrapPanel, **inside `TempSensorsPanel`** per D-05 reconsideration:

> ⚠️ **Spec resolution of CONTEXT.md D-05 ambiguity:** CONTEXT.md D-05 says "Help text stays enabled when sub-panel is greyed" and states it sits **outside** `TempSensorsPanel`. The corresponding note in `<specifics>` repeats "Place it OUTSIDE `TempSensorsPanel`." **This UI-SPEC honors D-05 verbatim:** the help text `<TextBlock>` lives as the **next sibling** of `TempSensorsPanel`, at the same indentation level as the master checkbox — NOT inside `TempSensorsPanel`. This guarantees that when `TempSensorsPanel.IsEnabled = false`, the help text remains fully readable (not greyed). Rationale per D-05: users reading "why are these checkboxes greyed out?" must still see the disclaimer that explains it.

Revised sequence (authoritative):

1. `<CheckBox x:Name="ChkTempsVisible" Content="Show Temps Line" Margin="0,0,0,10" />`
2. `<StackPanel x:Name="TempSensorsPanel" Margin="16,0,0,6">` wrapping only the 4-checkbox WrapPanel
3. `<TextBlock>` — muted disclaimer, at root-level of the tab body (outside TempSensorsPanel), `Foreground="#FF999999" FontSize="11" TextWrapping="Wrap" Margin="16,0,0,0"` (the 16px left margin visually aligns it with the sub-panel content it describes; stays enabled when master toggle is off)

### 2c. Canonical XAML skeleton

```xml
<!-- ===== TEMPS TAB ===== -->
<TabItem Header="Temps">
    <StackPanel Margin="12">

        <!-- Master toggle (TEMP-TAB-02; gates TempSensorsPanel per D-04) -->
        <CheckBox x:Name="ChkTempsVisible"
                  Content="Show Temps Line"
                  Margin="0,0,0,10"
                  Checked="ChkTempsVisible_Changed"
                  Unchecked="ChkTempsVisible_Changed"/>

        <!-- Per-sensor sub-panel (TEMP-TAB-03; indent 16px; master-gated IsEnabled per D-04) -->
        <StackPanel x:Name="TempSensorsPanel" Margin="16,0,0,6">
            <WrapPanel Width="270">
                <!-- Ordering locked: CPU, GPU, Mobo, NVMe (row-major) -->
                <CheckBox x:Name="ChkTempCpuVisible"  Content="CPU"  Width="86" Margin="0,0,0,5"
                          Checked="ChkTempCpuVisible_Changed"  Unchecked="ChkTempCpuVisible_Changed"/>
                <CheckBox x:Name="ChkTempGpuVisible"  Content="GPU"  Width="86" Margin="0,0,0,5"
                          Checked="ChkTempGpuVisible_Changed"  Unchecked="ChkTempGpuVisible_Changed"/>
                <CheckBox x:Name="ChkTempMoboVisible" Content="Mobo" Width="86"
                          Checked="ChkTempMoboVisible_Changed" Unchecked="ChkTempMoboVisible_Changed"/>
                <CheckBox x:Name="ChkTempNvmeVisible" Content="NVMe" Width="86"
                          Checked="ChkTempNvmeVisible_Changed" Unchecked="ChkTempNvmeVisible_Changed"/>
            </WrapPanel>
        </StackPanel>

        <!-- Help text (TEMP-TAB-03 verbatim; outside TempSensorsPanel per D-05) -->
        <TextBlock Text="CPU and NVMe readings may require elevated access or a helper driver (e.g. PawnIO) on some hardware; disabled checkboxes indicate the sensor is unavailable on this machine."
                   Foreground="#FF999999"
                   FontSize="11"
                   TextWrapping="Wrap"
                   Margin="16,0,0,0"/>

    </StackPanel>
</TabItem>
```

This skeleton is the **authoritative** layout contract. The planner MUST NOT vary `x:Name` identifiers (they are referenced in code-behind); may not reorder the four checkboxes; may not move the help text inside `TempSensorsPanel`; may not rename the tab header. All other XAML formatting (indentation, line-wrapping) is stylistic discretion.

## Interaction Contract

### Master toggle `ChkTempsVisible`

| Trigger | Effect |
|---------|--------|
| User checks/unchecks | Fires `TempsLineVisibleChanged(bool)` event (D-11); MainWindow handler mutates `_settings with { TempsLineVisible = e }` and calls `SettingsService.Save(_settings)` (D-12); NO widget render path in Phase 78 (Phase 79 wires render). |
| Programmatic set during `PopulateControls` / `RefreshControls` | `_suppressEvents=true` gate at line 60 / 116 prevents event firing (established pattern). IsChecked is set from `SettingsSnapshot.TempsLineVisible`. |
| Direct effect on `TempSensorsPanel.IsEnabled` | Toggling the master checkbox calls `TempSensorsPanel.IsEnabled = ChkTempsVisible.IsChecked == true` in `ChkTempsVisible_Changed` (D-04). Mirrors `ChkGhostMode_Changed` → `GhostFadeRadiusPanel.IsEnabled` precedent. |
| Effect on help-text TextBlock | **None.** Help text stays `IsEnabled=true` regardless of master toggle (D-05). |

### Per-sensor checkboxes `ChkTempCpuVisible` / `ChkTempGpuVisible` / `ChkTempMoboVisible` / `ChkTempNvmeVisible`

| Trigger | Effect |
|---------|--------|
| User checks/unchecks (when enabled) | Fires `TempCpuVisibleChanged(bool)` / `TempGpuVisibleChanged(bool)` / `TempMoboVisibleChanged(bool)` / `TempNvmeVisibleChanged(bool)` event (D-11); MainWindow handler mutates `_settings with { TempXVisible = e }` and calls `SettingsService.Save(_settings)` (D-12). |
| User clicks a disabled checkbox (`IsEnabled=false`) | WPF default — click is ignored; no event fires; no state change. |
| Programmatic set during `PopulateControls` / `RefreshControls` | `_suppressEvents=true` gate prevents event firing. IsChecked set from snapshot value (D-06: disabled checkbox still reflects stored value, e.g. ticked-but-greyed when `TempNvmeVisible=true` on hardware where NVMe is N/A). |

### N/A evaluation (D-01, D-02, D-03, D-06, D-07)

**Runs in `RefreshControls(SettingsSnapshot s)`, once per invocation.** Not live, not polled. Called in exactly three situations:

1. Settings window open (first paint via `PopulateControls`).
2. External `RefreshControls` call after a settings mutation elsewhere (e.g. `ResetToDefaults`, tray-menu toggle that syncs back).
3. After `ResetToDefaults` (D-14 — Reset resets values, then re-runs N/A detection).

Algorithm per call:

```
if (!_temperatureService.IsReady):
    # D-02 optimistic path — treat all as available
    for each of CPU/GPU/Mobo/NVMe:
        checkbox.IsEnabled = true
        checkbox.Content = label          # no suffix
else:
    # IsReady=true — evaluate sentinels (D-01)
    for each of CPU/GPU/Mobo/NVMe:
        if (_temperatureService.<Kind>TempC < 0f):
            checkbox.IsEnabled = false
            checkbox.Content = label + " (N/A)"    # D-07 literal suffix
        else:
            checkbox.IsEnabled = true
            checkbox.Content = label
```

**Checkbox `IsChecked` is set unconditionally from the snapshot in all branches** (D-06 — the stored value is authoritative even when the checkbox is disabled). Order of assignment inside `PopulateControls`: set `IsChecked` first, then evaluate N/A and set `IsEnabled` + `Content`. This guarantees the disabled-but-checked visual state (greyed tick) when `TempNvmeVisible=true` on N/A hardware.

### Master-off interaction with N/A

When `TempsLineVisible = false` (master off), `TempSensorsPanel.IsEnabled = false` globally greys the entire panel. This is a **different** greying than N/A: the stored-value greyed tick is already visible for any pre-checked sensor. WPF's `IsEnabled=false` on a parent cascades to children; the N/A-disabled checkboxes just stay disabled (double-disabled is idempotent). No visual distinction is required between "disabled because master off" and "disabled because N/A" — both produce a greyed checkbox with the stored tick state. The " (N/A)" suffix disambiguates per-sensor unavailability.

## State Matrix

Canonical rendering of each `(master, stored, availability)` combination per checkbox:

| Master toggle | Stored (`TempXVisible`) | Hardware (`<Kind>TempC`) | `IsReady` | Checkbox `IsEnabled` | Checkbox `IsChecked` | Checkbox `Content` |
|---------------|-------------------------|--------------------------|-----------|----------------------|----------------------|---------------------|
| ON | true | ≥0f | true | true | true | `CPU` (live sensor) |
| ON | false | ≥0f | true | true | false | `CPU` |
| ON | true | <0f (−1f) | true | **false** | **true** (greyed tick, D-06) | `CPU (N/A)` |
| ON | false | <0f | true | false | false | `CPU (N/A)` |
| ON | any | any | **false** (cold start) | true (D-02 optimistic) | stored | `CPU` (no suffix) |
| OFF | true | ≥0f | true | **false** (master-off cascade) | true (greyed tick) | `CPU` |
| OFF | true | <0f | true | false (double-disabled) | true (greyed tick) | `CPU (N/A)` |

Help text `Foreground` / `IsEnabled` is constant across every row: `#FF999999`, enabled. (D-05.)

## Accessibility

| Concern | Contract |
|---------|----------|
| Keyboard nav | TabItems participate in default WPF tab-order; inside the Temps tab, Tab key traverses `ChkTempsVisible` → `ChkTempCpuVisible` → `ChkTempGpuVisible` → `ChkTempMoboVisible` → `ChkTempNvmeVisible`. The help-text `TextBlock` is non-focusable (read-only). Disabled checkboxes are skipped by WPF's default tab navigation. |
| Space key | Toggles focused checkbox (WPF default). |
| Screen reader | WPF default `AutomationProperties` — the checkbox `Content` string IS the accessible name, so screen readers read `"CPU, checkbox, checked"` or `"CPU (N/A), checkbox, disabled, checked"` — the literal suffix is part of the name per D-07/D-09 (explicitly chosen over tooltips for screen-reader friendliness). |
| Explicit AutomationProperties | **None required.** The literal label + " (N/A)" suffix IS the accessible name; no `AutomationProperties.HelpText` override. The help-text `TextBlock` is self-narrating. |
| Focus visual | WPF default focus ring on CheckBox (honored by Dark theme). No override. |
| Color-only communication | None — the " (N/A)" suffix communicates availability in text, independent of the disabled-grey color cue. Users relying on high-contrast themes or screen readers get the same information. |
